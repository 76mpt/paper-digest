# 研究工作的通用規則（所有專案適用）

這些規則來自一次代價很大的錯誤：資料前處理的 bug 靜默存在了五個月，整條實驗線的結論在投稿前被推翻（2026-11，RAC 專案，細節見 D:/Research 的 memory: fps-pipeline-gap、reproduce-before-build）。

## 1. 先重現，再做實驗
- 以某篇論文或公開模型為基礎時，**第一件事**是在「我們實際要用的那條資料／訓練／評估流程」上，用官方 checkpoint 和論文的評估協定，重現論文的主數字。
- **每次換環境、換機器、換資料版本或前處理，都要重做一次**。在一個環境重現成功，不代表另一個環境也對。
- 重現的數字（含評估協定）要記下來，當作日後隨時可以回頭檢查的基準。

## 2. 解釋不了的差距一律先當成 bug
- 和論文或預期之間的差距，只要大於雜訊，在找到確切原因之前都視為 bug。
- 不要接受「看起來合理」的解釋（例如「套件版本不同」）。先提出並執行**最便宜、能區分不同假說的對照實驗**，驗證過的結論才能寫進 memory 或文件。
- 寫進 memory 的解釋要標明是「已驗證」還是「假說」。

## 3. 資料流程要能自我檢查
- 在程式裡檢查資料的一致性：實際解碼的影格數／樣本數、特徵長度，和標註檔裡的長度、時長是否吻合。對不上時要報錯，不能靜默截斷或補齊。
- 只保留**一個**正式的資料來源。任何偏離原論文的前處理（重新取樣、縮放、重新壓縮、截斷）都要寫下原因，並確認標註是否需要同步換算。
- 為了硬體限制所做的妥協（例如截斷長度、降低解析度）要標明是暫時的，換到更好的硬體時要回頭檢查。

## 4. 結果越符合預期越要懷疑
- 一個漂亮的理論剛好解釋了觀察到的現象時，先排除資料或流程的假象，再相信它。
- 分析用的子集（例如「高頻」「困難樣本」）要確認沒有和干擾變數（例如影片原生 fps、來源、解析度）綁在一起。
- 和原論文協定的對齊不能當成「最後再整理」的工作：它是驗證，要放在一開始。
